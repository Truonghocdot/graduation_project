# Thiết kế database

> Trạng thái: **Implemented v0.1 - bám theo business baseline v1.0**
>
> Database mục tiêu: **PostgreSQL**

Bộ tài liệu này chuyển các flow nghiệp vụ thành schema có thể triển khai bằng Laravel migrations. Database là nguồn dữ liệu chuẩn cho tài khoản, đơn/chuyến, thanh toán và audit; Redis chỉ giữ presence, geo index và cache ngắn hạn.

Schema đã được triển khai tại `worker/database/migrations/` và có contract test tại `worker/tests/Feature/Database/DatabaseSchemaTest.php`.

## Quy ước vật lý

### Khóa và định danh

- Primary key nội bộ: `BIGINT GENERATED BY DEFAULT AS IDENTITY`, tương ứng Laravel `$table->id()`.
- Resource lộ qua API có thêm `public_id UUID UNIQUE`, UUID được sinh ở application layer.
- Foreign key dùng hậu tố `_id`, cùng kiểu `BIGINT` với bảng cha.
- Không lộ primary key tăng dần trong API mobile.

### Thời gian

- Dùng `TIMESTAMPTZ` cho thời điểm nghiệp vụ.
- Database và server lưu UTC; client hiển thị `Asia/Ho_Chi_Minh`.
- Bảng mutable có `created_at`, `updated_at`; chỉ thêm `deleted_at` khi cần soft delete.
- Ledger, status history, audit và outbox không soft delete.

### Tiền

Business baseline yêu cầu kiểu `float`. PostgreSQL dùng `DOUBLE PRECISION`, Laravel dùng `$table->double()`.

- Currency hiện tại cố định `VND` nhưng vẫn lưu cột `currency CHAR(3)` ở transaction tài chính.
- Làm tròn về đơn vị VND trước khi ghi các tổng tiền cuối cùng.
- Không so sánh số tiền float bằng phép bằng tuyệt đối; dùng tolerance cấu hình khi đối soát.
- Snapshot giá lưu trên quote/order/payment để thay đổi cấu hình không làm đổi giao dịch cũ.

> Rủi ro kỹ thuật: floating point có sai số nhị phân. Nếu quyết định sản phẩm thay đổi, ưu tiên migration sang `NUMERIC(18,2)` hoặc integer VND trước khi có dữ liệu production.

### Trạng thái và enum

- Dùng `VARCHAR(40)`/`VARCHAR(50)` kết hợp PHP backed enum và `CHECK` constraint.
- Không dùng PostgreSQL native enum để tránh migration phức tạp khi bổ sung trạng thái.
- Giá trị enum dùng `UPPER_SNAKE_CASE` như tài liệu flow.

### JSON

`JSONB` chỉ dùng cho snapshot bất biến, metadata linh hoạt và payload tích hợp. Dữ liệu cần filter/join thường xuyên phải có cột riêng.

### Xóa dữ liệu

- Không hard delete order/booking, payment, ledger, settlement, status history, ticket, incident và audit.
- User, driver, vehicle, vehicle type, voucher dùng trạng thái active/inactive hoặc soft delete.
- Foreign key tài chính ưu tiên `RESTRICT`; dữ liệu phụ thuần túy có thể `CASCADE` theo bảng cha.

## Ranh giới lưu trữ

| Dữ liệu | PostgreSQL | Redis |
|---|---|---|
| User, driver, vehicle, pricing | Nguồn chuẩn | Cache tùy chọn |
| Trạng thái order/booking | Nguồn chuẩn | Snapshot để broadcast tùy chọn |
| Vị trí tài xế | Một snapshot cuối cùng | Snapshot hiện tại + TTL + geo index |
| Lịch sử hành trình | Không lưu | Không lưu sau TTL |
| Presence/socket room | Không | Có |
| Wallet/payment/settlement | Nguồn chuẩn | Lock/cache ngắn hạn, không là số dư chuẩn |
| Event outbox/dedup | Nguồn chuẩn | Cache dedup bổ sung tùy chọn |

## Khoảng cách với schema hiện tại

Schema trong `worker/` mới là starter kit và cần migration chuyển đổi trước khi triển khai domain:

| Hiện tại | Mục tiêu |
|---|---|
| `users.email` bắt buộc và unique | `users.phone` bắt buộc/unique; `email` nullable và chỉ là hồ sơ |
| `email_verified_at` | `phone_verified_at` |
| `password_reset_tokens` khóa theo email | Reset password theo `user_id`/số điện thoại và token hash |
| Chưa có `status`, `public_id`, role | Bổ sung user status, UUID public và `user_roles` |
| `.env.example` dùng `DB_CONNECTION=psql` | Laravel connection key đúng là `pgsql` |

Các bảng framework `personal_access_tokens`, `jobs`, `job_batches`, `failed_jobs` được giữ lại và không mô tả lại trong data dictionary nghiệp vụ.

## Nguyên tắc transaction

1. State transition và `status_histories` ghi trong cùng transaction.
2. Wallet balance cache, ledger transaction và ledger entries ghi nguyên tử.
3. Tạo order/booking, trừ ví, dùng voucher và ghi outbox là một transaction logic; nếu tách provider call thì dùng state machine + idempotency.
4. Accept offer khóa service request và driver; chỉ một assignment active được commit.
5. Publish RabbitMQ chỉ sau commit thông qua outbox.
6. Webhook SePay, command hoàn thành, settlement, refund và withdrawal đều có idempotency key/unique provider reference.
